# pan_tilt

Firmware for a pan/tilt turret built on an **STM32F411CEU6** ("BlackPill"-class
board). Two hobby servos aim the head, a laser marks the target, an HC-SR04
measures range, and everything is driven over a single UART link from a
Raspberry Pi.

> **Status: work in progress.** The pieces marked below are built and verified
> on hardware. The rest is not written yet.

| Subsystem | State |
|---|---|
| Laser output (PB0) | ✅ working, UART controlled |
| UART receive + line framing | ✅ working |
| UART transmit + telemetry | ✅ working |
| HC-SR04 ranging | ✅ working |
| `KEY:VALUE` command parser | ⬜ not started |
| Servo control (TIM3 PWM) | ⬜ not started |
| Raspberry Pi host software | ⬜ not started |

## Design

Everything is interrupt-driven and the main loop never blocks. UART bytes and
echo edges arrive as interrupts, which do the minimum work and hand off to the
main loop; the loop spins continuously and is always free to respond.

The single exception is a 12 µs busy-wait used to generate the HC-SR04 trigger
pulse — 0.012% of each measurement cycle, taken deliberately rather than
spending a second timer on it. It is commented as such in `ultrasonic.c`.

## Hardware

| Pin | Function |
|---|---|
| PA6 | TIM3_CH1 PWM — pan servo |
| PA7 | TIM3_CH2 PWM — tilt servo |
| PA9 | USART1 TX → Pi RXD |
| PA10 | USART1 RX ← Pi TXD |
| PB0 | Laser, via an NPN low-side switch |
| PB6 | TIM4_CH1 input capture — HC-SR04 ECHO |
| PB7 | GPIO output — HC-SR04 TRIG |

**Laser drive.** PB0 does not power the laser directly — a GPIO pin supplies
about 8 mA usefully, and the laser needs ~25 mA. PB0 drives the base of an NPN
transistor through a 1 kΩ series resistor; the laser runs from the 3V3 rail
with the transistor switching its low side.

**HC-SR04.** The module runs at 5 V and its ECHO output is 5 V logic. Check
that PB6 is 5 V tolerant (`FT` in the datasheet pin table) before connecting
it directly, or fit a divider — 1 kΩ from ECHO to PB6, 2 kΩ from PB6 to GND.

**Pi link.** Both sides are 3.3 V logic, so no level shifter. Cross the data
lines, share ground, and leave the Pi's 5 V unconnected.

## Serial protocol

115200 8N1. Lines are terminated by `\n` or `\r`; both are accepted.

**Commands to the board**

```
LASER:ON
LASER:OFF
```

**Replies**

```
OK
ERR:BADCMD
```

**Telemetry from the board**

```
BOOT:pan_tilt      once at startup
RANGE:47           centimetres, about 10 times per second
```

The intended full grammar is `KEY:VALUE[,KEY:VALUE...]`, so a single line can
carry several commands (`H:1500,V:1200,LASER:ON`). The parser that makes this
general is not written yet — right now only the two laser commands are matched.

## Toolchain

- [Arm GNU Toolchain](https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads) (`arm-none-eabi-gcc`), tested with 15.2
- GNU Make
- A SEGGER J-Link probe and the [J-Link software pack](https://www.segger.com/downloads/jlink/)
- Optional: STM32CubeMX, to regenerate from `pan_tilt.ioc`

Paths to the toolchain and J-Link are set at the top of `GNUmakefile` and in
`.vscode/settings.json`. They point at typical macOS locations — **edit them
for your machine.**

## Build and flash

```bash
make            # build
make flash      # build, program over SWD, and run
make range      # print live HC-SR04 readings
make help       # list all targets
```

Debugging: `make gdbserver` in one terminal, `make debug` in another. In VS
Code, F5 builds, flashes, and breaks at `main` (needs the Cortex-Debug
extension).

## Repository layout

```
Core/Inc, Core/Src   application code and CubeMX output
Drivers/             ST HAL and CMSIS, vendored
GNUmakefile          hand-written targets (flash, debug, range)
Makefile             generated by CubeMX — do not edit
pan_tilt.ioc         CubeMX project
```

### A note on CubeMX

`Makefile` is regenerated from `pan_tilt.ioc` and any edit to it is lost. All
hand-written targets live in `GNUmakefile`, which GNU Make reads in preference
to `Makefile` and which CubeMX never touches. It also re-scans `Core/Src`, so
new source files are compiled without editing anything.

Application code lives in its own modules (`laser.c`, `ultrasonic.c`,
`comms.c`) rather than in `main.c`, so regeneration cannot clobber it. What
little sits in `main.c` is inside `USER CODE` markers.

## Safety

Even a low-power laser diode is an eye hazard, and this one sits on a head
that moves under software control. Point it at a wall, not a window, and keep
your eyes out of the beam while testing.
